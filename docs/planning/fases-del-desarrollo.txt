1. VISIÓN GENERAL DEL SISTEMA
------------------------------------------------------------

El sistema busca controlar empresas cliente, obligaciones fiscales, tareas contables, tareas administrativas, calendarios tributarios, usuarios, permisos, alertas, correos, portal cliente, documentos, auditoría y reportes gerenciales.

El sistema debe permitir:

1. Crear empresas automáticamente desde el PDF del RUT.
2. Detectar obligaciones fiscales nacionales y municipales.
3. Cargar calendarios fiscales por año, impuesto y municipio.
4. Generar tareas fiscales automáticas.
5. Crear tareas manuales, contables, administrativas, operativas y recurrentes.
6. Gestionar usuarios internos y usuarios cliente.
7. Asignar permisos por rol, cargo y checklist personalizada.
8. Proteger datos sensibles de clientes.
9. Solicitar documentos al cliente.
10. Permitir al cliente cargar soportes y revisar estados permitidos.
11. Enviar alertas internas y correos reales.
12. Consolidar dashboards, reportes e indicadores.
13. Mantener auditoría y trazabilidad.
14. Manejar configuración general sin tocar código.
15. Preparar el sistema para operar como SaaS multiempresa.

3. FLUJO GENERAL INTEGRADO
------------------------------------------------------------

1. Un usuario autorizado carga el PDF del RUT.
2. El sistema extrae datos automáticamente.
3. El usuario revisa y confirma la información.
4. Se crea la empresa.
5. El sistema analiza responsabilidades tributarias, actividad económica, municipio y régimen.
6. Se sugieren o crean obligaciones fiscales.
7. El usuario confirma las obligaciones.
8. El administrador carga calendarios fiscales nacionales o municipales.
9. El sistema genera tareas fiscales solo para empresas activas.
10. El gerente crea tareas manuales o recurrentes no fiscales si aplica.
11. Los usuarios trabajan tareas según permisos y empresas asignadas.
12. Las tareas fiscales pasan por liquidación, revisión, presentación y pago.
13. Las tareas generales pasan por ejecución, evidencia, revisión y cierre.
14. El sistema solicita documentos al cliente cuando una tarea lo requiere.
15. El cliente entra al portal, consulta su empresa y carga soportes permitidos.
16. El sistema genera alertas internas.
17. El sistema valida si corresponde enviar correo.
18. El correo se envía solo si pasa validaciones.
19. El dashboard consolida cumplimiento, riesgos, pagos, tareas, alertas y usuarios.
20. La auditoría registra acciones sensibles.
21. Los respaldos protegen la información.
22. La configuración permite ajustar reglas, plantillas, alertas, permisos y parámetros sin cambiar código.
23. El sistema queda preparado para operar como SaaS mediante separación por organización o tenant.

------------------------------------------------------------
4. REGLAS TRANSVERSALES DEL SISTEMA
------------------------------------------------------------

1. No eliminar información histórica.
2. Desactivar, suspender, archivar o versionar en lugar de borrar.
3. Solo empresas activas generan nuevas tareas fiscales desde calendario.
4. Las tareas manuales o recurrentes deben respetar el estado de la empresa.
5. Una empresa suspendida, inactiva o archivada sale del flujo operativo activo.
6. Una tarea fiscal puede estar liquidada y presentada, pero pendiente de pago por el cliente.
7. El no pago del cliente no afecta el cumplimiento operativo interno si existe trazabilidad.
8. No todas las tareas dependen de impuestos.
9. El sistema debe permitir tareas manuales y recurrentes.
10. El usuario solo debe ver lo necesario para cumplir su trabajo.
11. Los datos sensibles del cliente deben protegerse por permisos.
12. El cliente solo ve información de su propia empresa y únicamente lo autorizado.
13. Toda acción sensible debe generar auditoría.
14. La alerta interna siempre debe crearse.
15. El correo solo debe enviarse si pasa validaciones.
16. El fallo del correo no elimina la alerta interna.
17. La configuración debe permitir ajustes sin despliegues de código.
18. Las solicitudes al cliente deben quedar trazadas.
19. Los documentos cargados deben quedar asociados a empresa, tarea, solicitud o evidencia.
20. El sistema debe contemplar multiempresa o multi-tenant para crecer como SaaS.

------------------------------------------------------------
5. GESTIÓN DE ESTADOS DE EMPRESA
------------------------------------------------------------

Estados:

borrador:
Se inició la creación o se cargó un RUT, pero aún no se confirmó.

pendiente_revision:
La empresa tiene datos incompletos o extracción parcial.

activa:
Empresa operativa. Participa en obligaciones, calendarios, tareas, alertas y dashboards.

suspendida:
Empresa pausada temporalmente. No genera nuevas tareas mientras esté suspendida, pero puede reactivarse.

inactiva:
Empresa que ya no se gestiona operativamente. Conserva histórico.

archivada:
Empresa cerrada para operación normal. Solo visible para consulta histórica o auditoría.

Regla:
Una empresa suspendida, inactiva o archivada no debe generar nuevas tareas fiscales, tareas recurrentes, obligaciones automáticas ni alertas futuras operativas. Conserva todo su histórico.

FASE 1 - CREACIÓN AUTOMÁTICA DE EMPRESA DESDE PDF RUT
------------------------------------------------------------

Objetivo:
Crear empresas a partir del cargue del PDF del RUT, extrayendo información automáticamente y exigiendo revisión humana antes de guardar.

Flujo:
1. Usuario autorizado carga PDF del RUT.
2. El sistema valida que sea PDF.
3. El sistema guarda archivo temporal.
4. El sistema extrae texto.
5. El sistema interpreta campos.
6. El sistema muestra formulario precargado.
7. Usuario revisa, corrige y confirma.
8. Sistema crea empresa.
9. Sistema asocia ubicación, actividad económica, responsabilidades, representante legal y documento RUT.
10. Sistema guarda trazabilidad.

FASE 9 - PORTAL DEL CLIENTE
------------------------------------------------------------

Objetivo:
Crear un portal limitado y seguro para que el cliente pueda ingresar, consultar el estado de su empresa, ver pagos pendientes, cargar soportes, responder solicitudes y consultar información compartida.

Justificación:
El cliente necesita visibilidad y capacidad de respuesta, pero sin acceder a información interna, otros clientes, comentarios privados ni gestión operativa interna.

Alcance del portal cliente:
El cliente puede:

- Iniciar sesión.
- Ver su empresa o empresas asociadas.
- Ver estado general de obligaciones compartidas.
- Ver pagos pendientes.
- Ver pagos vencidos.
- Cargar soporte de pago.
- Ver soportes compartidos.
- Descargar documentos compartidos.
- Ver solicitudes de documentos.
- Responder solicitudes.
- Cargar documentos solicitados.
- Ver alertas dirigidas al cliente.
- Ver historial básico visible.
- Actualizar datos de contacto permitidos, si se configura.

El cliente no puede:

- Ver otras empresas.
- Ver usuarios internos.
- Ver comentarios internos.
- Ver auditoría interna.
- Ver documentos no compartidos.
- Ver datos comerciales internos.
- Ver reportes gerenciales internos.
- Cambiar obligaciones fiscales.
- Cambiar calendarios.
- Cerrar tareas internas.
- Ver tareas no compartidas.

Entidades:
- PortalClienteConfig.
- ClienteEmpresaAcceso.
- DocumentoCompartidoCliente.
- AlertaCliente.
- ActividadPortalCliente.
- PreferenciaClienteNotificacion.

Reglas:
- El cliente solo ve empresas asociadas en EmpresaUsuario.
- El cliente solo ve información marcada como visibleParaCliente.
- Los comentarios internos no se muestran.
- Los documentos deben marcarse como compartidos para ser visibles.
- El cliente puede cargar soportes, pero estos deben pasar a revisión interna.
- El cliente no puede eliminar documentos una vez cargados; puede solicitar reemplazo.
- Todo acceso del cliente debe quedar auditado.
- Si el usuario cliente se desactiva, no se elimina la empresa.

Vistas:
- Inicio cliente.
- Estado de mi empresa.
- Pagos pendientes.
- Solicitudes de documentos.
- Cargar soporte.
- Documentos compartidos.
- Alertas.
- Historial visible.

Estados de documentos cargados por cliente:
- recibido.
- en_revision.
- aprobado.
- rechazado.
- reemplazado.

Resultado esperado:
Portal cliente seguro, útil y limitado.

FASE 10 - SOLICITUDES DE DOCUMENTOS E INFORMACIÓN AL CLIENTE
------------------------------------------------------------

Objetivo:
Crear un módulo para solicitar, recibir, revisar y aprobar documentos o información requerida al cliente para cumplir tareas contables, fiscales o administrativas.

Justificación:
Muchas tareas dependen de documentos del cliente. Sin este módulo, la operación queda incompleta y se pierde trazabilidad.

Ejemplos de documentos solicitados:
- Extractos bancarios.
- Facturas de venta.

- Nómina.
- Planillas de seguridad social.
- Comprobantes de pago.
- Certificados.
- Recibos.
- Soportes contables.
- Información para impuestos.
- Soporte de pago de declaración.
- Documentos legales.
- Actualización de RUT.
- Cámara de comercio.
- Contratos.
- Información de cartera.

Entidades:

Estados de solicitud:

- pendiente.
- recibido.
- en_revision.
- aprobado.
- rechazado.

Flujo:
1. Usuario interno crea solicitud.
2. Selecciona empresa y cliente destinatario.
3. Define documentos requeridos.
4. Define fecha límite.
5. Envía solicitud.
6. Sistema crea alerta interna y alerta cliente.
7. Si aplica, envía correo al cliente.
8. Cliente carga documentos en portal.
9. Sistema registra recepción.
10. Usuario interno revisa.
11. Aprueba o rechaza.
12. Si rechaza, solicita corrección.
13. Documentos aprobados pueden asociarse a tareas o evidencias.

Reglas:

- Una tarea puede requerir una o varias solicitudes al cliente.
- Los documentos cargados por cliente no se eliminan; se reemplazan.
- Si la solicitud vence, genera alerta.
- Si el cliente carga documento incorrecto, se rechaza con motivo.
- El cliente solo ve sus solicitudes.
- El gerente puede ver todas.
- El usuario responsable ve las solicitudes de sus empresas asignadas.
- Los documentos aprobados pueden alimentar evidencias de tarea.
- Todo cambio queda en historial.

Alertas:
- solicitud_documento_enviada.
- solicitud_documento_pendiente.
- solicitud_documento_por_vencer.
- solicitud_documento_vencida.
- documento_cliente_recibido.
- documento_cliente_rechazado.
- documento_cliente_aprobado.

Resultado esperado:
Control total de información solicitada al cliente.

TECNOLOGÍAS RECOMENDADAS
------------------------------------------------------------

Tipo de sistema:
Aplicación web en navegador, responsive, con posibilidad de evolucionar a SaaS.

------------------------------------------------------------
Frontend recomendado
------------------------------------------------------------

Opción principal:
- React.
- Vite.
- TypeScript.
- Tailwind CSS.

Librerías útiles:
- React Router para rutas.
- TanStack Query para manejo de datos.
- React Hook Form para formularios.
- Zod para validaciones.
- shadcn/ui para componentes visuales.
- Recharts para gráficos del dashboard.
- Lucide Icons para iconografía.

Justificación:
Rápido, moderno, mantenible y adecuado para dashboards, formularios y sistemas administrativos.

------------------------------------------------------------
Backend recomendado
------------------------------------------------------------

Opción principal:
- Node.js.
- Express o NestJS.
- TypeScript.

Recomendación:
Para un sistema grande y ordenado, NestJS puede ser mejor por módulos, servicios, controladores, validaciones y escalabilidad.

Para avanzar más rápido si el equipo está aprendiendo:
Express con buena estructura por módulos también sirve.

Librerías:
- Prisma ORM o Mongoose según base de datos.
- Zod o class-validator para validar datos.
- Multer para carga de archivos.
- Nodemailer para correos.
- JWT para autenticación.
- bcrypt para contraseñas.
- Helmet para seguridad HTTP.
- express-rate-limit para limitar intentos.
- Winston o Pino para logs.

------------------------------------------------------------
Base de datos recomendada
------------------------------------------------------------

Opción recomendada para este sistema:
- PostgreSQL.

Razones:
- Relacional.
- Fuerte para entidades como empresas, usuarios, permisos, tareas, obligaciones, calendarios.
- Mejor para reportes.
- Mejor para integridad de datos.
- Buena base para SaaS.

Alternativa:
- MongoDB puede servir si ya está avanzado el proyecto, pero para este caso PostgreSQL es más ordenado y sólido.

ORM recomendado:
- Prisma.
